## 2. Мета роботи

Реалізувати типізовані запити до колекції `List<Trip>` засобами Stream API: фільтрацію, відображення, групування, статистику, сортування з обмеженням кількості та пошук через `Optional`. Перевірити граничні випадки, відсутність змін вхідної колекції та еквівалентність результатів звичайному циклу.

## 3. Організація даних і API

Запити зосереджені в утилітарному класі `TripQueries`; кожен метод приймає `List<Trip>` і повертає результат, не друкуючи його та не змінюючи список. Це відокремлює обробку даних від консольного вводу-виводу. Рейси залишаються типізованими об'єктами `Trip`, `PassengerTrip` і `CargoTrip` із попередньої роботи.

## 4. Реалізовані запити

| Вимога варіанта 7 | Реалізація | Поведінка |
| --- | --- | --- |
| Відібрати рейси понад 100 км | `longTrips`: `filter` | Межа строга: рівно 100 км не включається |
| Отримати назви транспорту | `vehicleNames`: `map` | Початковий порядок і дублікати збережені |
| Згрупувати витрату на 100 км | `fuelByVehicle`: `groupingBy`, суми кілометрів і `calculatedFuelLiters()` | `100 * сумарне пальне / сумарні кілометри` для кожної групи |
| Порахувати статистику відстаней | `distanceStatistics`: `summarizingDouble` | `DoubleSummaryStatistics`: кількість, сума, середнє, мінімум і максимум |
| Повернути топ-N за відстанню | `topTrips`: сортування та `limit` | Відстань за спаданням, дата за зростанням; від'ємне N відхиляється |
| Знайти рейс за транспортом і датою | `findTrip`: `filter`, `findFirst` | `Optional<Trip>` містить перший збіг або є порожнім |

Порожній список дає порожні списки/мапу, нульову кількість у статистиці й порожній `Optional`. Назви транспортних засобів навмисно не дедуплікуються: це проєкція рядків, а не множина.

## 5. Демонстраційний набір і результати

Тестовий набір у `TripQueriesTest` містить шість рейсів, зокрема вантажний, значення на межі 100 км, однакові відстані з різними датами, повторний ключ пошуку та записи трьох транспортних засобів.

| Запит | Результат на шести записах |
| --- | --- |
| Відстань `> 100` | 3 рейси: 120, 150 і 120 км; запис рівно на 100 км не включений |
| Назви | `Bus A, Bus B, Truck, Bus A, Bus B, Bus A` |
| Витрата за транспортом | Bus A: `33 / 230 * 100 = 14.3478`; Bus B: `36 / 240 * 100 = 15.0000`; Truck: `22 / 150 * 100 = 14.6667` л/100 км |
| Статистика відстаней | кількість 6; сума 620 км; середнє 103.3333 км; мінімум 50 км; максимум 150 км |
| Топ-5 | Truck 150 км; Bus B 120 км від 2026-09-01; Bus B 120 км від 2026-09-02; Bus A 100 км; Bus A 80 км. Рейс на 50 км лишається шостим |
| Пошук Bus A за 2026-09-03 | Повертається перший запис із цим ключем (100 км); для відсутнього транспорту результат порожній |

Це синтетичні контрольні дані автоматичного тесту, не статистика реального перевізника.

## 6. Складений компаратор

У `topTrips` порядок задано як `Comparator.comparingDouble(Trip::getKm).reversed().thenComparing(Trip::getDate)`. Спершу більші відстані йдуть раніше; за однакового кілометражу дата порівнюється за зростанням. `limit(n)` застосовується після сортування. Тест перевіряє порядок двох рейсів по 120 км, `n = 0`, `n` більше розміру списку та від'ємне значення.

## 7. Порівняння Stream API зі звичайним циклом

У тесті `streamQueriesMatchLoopReference` для того самого набору шести записів звичайний цикл `for` окремо формує відфільтрований список і список назв, накопичує відстань та групові суми, знаходить min/max і перший збіг. Для топ-5 циклова версія сортує копію списку. Результати Stream API порівнюються з еталоном циклу; для чисел задано похибку `0.0001`. Це перевірка однаковості поведінки, а не швидкодії.

| Операція | Еталонний цикл | Stream API | Перевірка |
| --- | --- | --- | --- |
| Фільтр і проєкція | `if`, додавання в списки | `filter`, `map`, `toList` | списки рівні, порядок збережений |
| Групові суми | `Map` із ручними накопичувачами | `groupingBy`, `mapToDouble`, `sum` | витрата кожного транспорту збігається |
| Статистика | ручне накопичення суми, min, max | `summarizingDouble` | сума, min і max збігаються |
| Топ-5 | копія, `sort`, перші п'ять елементів | `sorted`, `limit` | послідовності рейсів рівні |
| Перший збіг | збереження першого елемента в циклі | `filter`, `findFirst` | повернуто той самий об'єкт |

## 12. Відповіді на контрольні питання (чернетка)

1. Stream API дає декларативно описати послідовність операцій над джерелом даних.
2. `filter` залишає елементи, для яких предикат повертає `true`.
3. `map` перетворює кожен елемент потоку на значення іншого типу або форми.
4. Проміжні операції зазвичай ліниві; термінальна операція запускає обробку.
5. `collect` збирає елементи потоку в контейнер або агрегат.
6. `groupingBy` класифікує елементи за ключем у мапу груп.
7. `summarizingDouble` обчислює кількість, суму, середнє, мінімум і максимум `double`-значень.
8. `reversed()` змінює напрямок критерію компаратора, а `thenComparing` додає критерій для нічиєї.
9. `limit(n)` залишає не більше перших `n` елементів упорядкованого потоку.
10. `Optional<T>` представляє наявне або відсутнє значення без `null` як результату пошуку.
11. `findFirst` повертає перший збіг відповідно до encounter order джерела.
12. `toList()` створює список результатів; методи запитів не змінюють вихідний список.
13. Для порожнього потоку статистика має count і sum 0, min/max нескінченні граничні значення, average дорівнює 0.
14. Групова витрата на 100 км: сумарні літри / сумарні кілометри * 100.
15. Для вантажного рейсу використовується поліморфний `calculatedFuelLiters()`, а не перевірка підтипу в запиті.
16. Строга умова `km > 100` не включає рейс рівно на 100 км.
17. За повторного ключа `findFirst` повертає перший за порядком запис.
18. `Optional.empty()` означає, що запис за заданими критеріями не знайдено.
19. Цикл зручний для покрокової мутації стану; Stream API описує перетворення й агрегування конвеєром операцій.
20. Еквівалентність способів перевіряється на тому самому наборі даних шляхом порівняння результатів, не часу виконання.
